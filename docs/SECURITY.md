# امنیت و حریم داده

تاریخ بازبینی: ۲۱ شهریور ۱۴۰۵ (2026-09-12)

## نسخه‌های پشتیبانی‌شده

اصلاح امنیتی روی آخرین نسخهٔ منتشرشده و شاخهٔ فعال توسعه اعمال می‌شود. برای نسخه‌های قدیمی‌تر تعهد پشتیبانی جداگانه‌ای وجود ندارد؛ پیش از گزارش، ایراد را در آخرین نسخهٔ قابل‌استفاده بازآزمایی کنید. نسخه‌های `rc` پیش‌انتشارند و نباید بدون ارزیابی مستقل در محیط حساس به‌کار روند.

## مرز اعتماد

- مرورگر مدیر، مرورگر پاسخ‌دهنده، reverse proxy، PostgreSQL، filesystem محلی و provider هوش مصنوعی مرزهای جدا هستند.
- پاسخ، نام فایل، متن فرم و خروجی مدل دادهٔ غیرقابل‌اعتمادند؛ هیچ‌کدام به‌عنوان HTML، SQL، مسیر فایل یا فرمان اجرا نمی‌شوند.
- دسترسی shell، حساب PostgreSQL و مالکیت کاربر سیستم خارج از کنترل برنامه‌اند و باید در میزبان محدود شوند.

## کنترل‌های پیاده‌شده

- Argon2id، نشست HttpOnly/SameSite، cookie امن، انقضای idle/absolute و ابطال نشست پس از reset رمز.
- سه نقش مدیر، طراح و مشاهده‌گر با تست endpoint؛ عملیات کاربران، provider و سلامت سیستم فقط مدیر.
- Cross-Origin Protection، CSP، HSTS در production، `nosniff`، Referrer/Permissions Policy و نبود CORS عمومی.
- query پارامتری، schema/flow validation، UUID پایدار و snapshot تغییرناپذیر انتشار.
- rate limit تفکیک‌شده، اعتماد به `X-Forwarded-For` فقط از CIDR proxy، honeypot، minimum-fill-time و Turnstile اختیاری.
- upload streaming با سقف، allowlist پسوند/MIME/magic، نام storage تولیدشده، مسیر خارج web root و download احراز‌شده.
- provider AI با HTTPS، منع redirect/userinfo، resolve دوباره در dial، رد private/link-local/metadata و allow-private صریح.
- AI فقط ابزارهای query محدود دارد؛ SQL/filesystem/export خام در اختیار مدل نیست و نمونهٔ متن رضایت مستقل می‌خواهد.
- backup با maintenance drain، checksum همهٔ اجزا، verify دوباره و secret-exclusion؛ restore فقط آفلاین و همراه safety backup. پنل فقط پس از تأیید صریح، درخواست `0600` اتمیک و بدون overwrite می‌سازد و process وب را کنترل‌شده تحویل systemd می‌دهد.
- log ساختاریافته request ID دارد و password، cookie، پاسخ، API key و محتوای فایل را ثبت نمی‌کند.

## secretها

`/etc/forms/forms.env` باید `root:forms` و `0640` باشد. کلید AI در data directory با `0600` ذخیره می‌شود و داخل DB، پاسخ API یا backup عادی قرار نمی‌گیرد. release نباید فایل environment، data directory، backup واقعی یا fixture حساس داشته باشد.

کلید provider برای احراز هویت، فقط در header درخواست به همان endpoint اعتبارسنجی‌شده‌ای که مدیر ذخیره کرده ارسال می‌شود؛ HTTPS الزامی است و HTTP فقط برای loopback با تأیید صریح پذیرفته می‌شود. کلید در prompt، آرگومان ابزار، رابط کاربری یا پاسخ API برنامه قرار نمی‌گیرد. redirect دنبال نمی‌شود تا header احراز هویت به مقصد دیگری نرود. مدیر باید provider را یک پردازشگر ثالث داده در نظر بگیرد و سیاست نگه‌داری دادهٔ آن را جداگانه بررسی کند.

## provider هوش مصنوعی

- این قابلیت اختیاری و در هر پروژه به‌صورت پیش‌فرض خاموش است؛ نبود provider یا مدل مانع ساخت، انتشار و دریافت پاسخ فرم نمی‌شود.
- ذخیرهٔ تنظیمات اتصال هیچ درخواست خارجی نمی‌فرستد. «آزمون اتصال» یک درخواست ساختگی برای اثبات streaming و ابزارها می‌فرستد و هیچ پاسخ واقعی فرم را همراه ندارد.
- داده تنها وقتی از سامانه خارج می‌شود که اتصال آزموده شده، قابلیت همان پروژه فعال باشد و کاربر پیامی ارسال کند. حالت پایه فقط schema و آمار تجمیعی را در اختیار provider می‌گذارد؛ نمونهٔ متن پاسخ‌دهنده رضایت صریح و جداگانه می‌خواهد.
- برنامه provider یا مدل جایگزین را خودکار انتخاب نمی‌کند. آزمون ناموفق وضعیت اتصال را «آماده نیست» می‌کند، ولی نشانی، نام مدل و secret ذخیره‌شده را تغییر نمی‌دهد.

## ریسک‌های باقی‌مانده

- ClamAV وابستگی اجباری نیست؛ فایل ناشناس parse یا اجرا نمی‌شود. سازمان‌های پرریسک باید scanner بیرونی را پیش از دسترسی اپراتور اضافه کنند.
- rate limit حافظه‌ای است و میان چند replica هماهنگ نمی‌شود؛ نسخهٔ فعلی برای یک process طراحی شده است.
- محرمانگی backup در حالت سکون به encryption دیسک/ذخیره‌ساز میزبان وابسته است. آرشیو عادی رمزگذاری داخلی ندارد.
- TLS در reverse proxy پایان می‌یابد؛ exposure مستقیم پورت برنامه خارج از loopback پشتیبانی نمی‌شود.

## کنترل dependency و release

هر release باید `npm audit --audit-level=moderate`، `govulncheck ./...` و `go test -race ./...` را اجرا کند و همراه `SHA256SUMS`، checksum آرشیو و CycloneDX SBOM ساخته شود. نتیجهٔ هر اجرا یک snapshot زمانی است و تضمین نبود آسیب‌پذیری آینده نیست؛ شواهد پذیرش جاری در [گزارش مرحلهٔ چهارم](PHASE-4-REPORT.md) و روش بازتولید در [راهنمای release](RELEASE-FA.md) ثبت می‌شود.

امضای minisign وقتی `FORMS_MINISIGN_SECRET_KEY` در محیط امن release runner تعیین شود ساخته می‌شود. کلید امضا نباید در مخزن یا workspace عمومی قرار گیرد.

## گزارش آسیب‌پذیری

اگر در صفحهٔ مخزن، گزینهٔ **Security → Report a vulnerability** در دسترس است، گزارش را از همان مسیر خصوصی GitHub ارسال کنید. اگر این قابلیت فعال نیست، گزارش را فقط به مالک همان استقرار از کانال امن سازمانی تحویل دهید. این پروژه تا زمانی که یک نشانی رسمی در خود مخزن منتشر نشده، هیچ ایمیل یا حساب ثالثی را به‌عنوان تماس امنیتی معرفی نمی‌کند.

گزارش باید نسخه و checksum باینری، مؤلفه یا مسیر اثرپذیر، روش بازتولید کم‌خطر، اثر احتمالی و راه کاهش پیشنهادی را داشته باشد. secret، cookie، dump پایگاه داده، فایل upload یا پاسخ واقعی افراد را ضمیمه نکنید؛ نمونهٔ مصنوعی و request ID پاک‌سازی‌شده کافی است. آسیب‌پذیری تأییدنشده را در issue، discussion یا pull request عمومی افشا نکنید.

برای اثبات، به دادهٔ دیگران دسترسی نگیرید، persistence نسازید، سرویس را از دسترس خارج نکنید و از مهندسی اجتماعی یا آزمون زیرساخت ثالث خودداری کنید. دریافت گزارش به‌معنای پذیرش اثر یا وعدهٔ زمان رفع مشخص نیست؛ وضعیت هماهنگی و افشای عمومی باید در همان کانال خصوصی توافق شود.
